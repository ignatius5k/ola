# Ola permission contract (SCRUM-37)

Status: proposed contract for the connected app. The current browser role selector is a demo control and does not enforce these permissions. This document defines backend outcomes for [the architecture](architecture.md); [SCRUM-38](implementation-index.md) adds the full state-transition matrix and tests.

## Authority and response rules

An invited Supabase Auth user may act in one workspace only while their `workspace_members` row is active. That row is the role authority (`analyst` or `reviewer` from [`shared/domain.js`](../shared/domain.js)); the verified user ID is the actor. A client-provided role, actor, `user_metadata`, localStorage value, case ID, file path or hidden button grants nothing. Every protected request verifies the user and current membership. Read policies and Storage policies separately enforce workspace scope. Sensitive writes go through an Edge Function plus a guarded database transaction; ordinary clients have no direct write grant to workflow, allocation, policy or audit tables.

Error precedence: absent/invalid identity → **401**; authenticated non-member or inactive membership → **403** without business data; known member asking for a disallowed role/action → **403**; absent or outside-workspace resource → **404** with the same safe message; stale version, competing allocation, idempotency-key reuse with changed input or invalidated snapshot → **409**; validly scoped but ineligible business input/transition → **422**; malformed envelope → **400**; unexpected failure → **500** with a request ID. RLS may produce an empty result for a denied direct Data API read; an application endpoint maps single-resource reads to 404. No error reveals another workspace's record, actor, reference or evidence path.

The matrix below uses **A** for an active Analyst, **R** for an active Reviewer, and **D** for denial. “Same workspace” is necessary for every allowed action; it is never sufficient by itself. Examples use synthetic records only.

## Record and transition constraints

- `claim`, `save_draft`, `add_evidence`, `submit`, `withdraw`, `return`, `approve`, `escalate` and `reopen` use `POST /functions/v1/case-action` with `{workspaceId,caseId,action,expectedVersion,idempotencyKey,payload}`. Each carries a positive version and a UUID key. The server checks state, assignment and workspace for every referenced case, posting, submission and attachment. [SCRUM-42](implementation-index.md) owns exact payload schemas and the stable error codes.
- `submit` snapshots original collection and proposed ledger UUIDs/hashes on the server. `evidenceIds` contains only optional uploaded attachment IDs. Submissions and decisions are historical. A return or withdrawal permits a new submission; an in-place edit of a pending snapshot is denied.
- A valid exact low-risk case can move to `auto_matched` without a human submission only if all policy checks pass, no ledger conflict exists and no revalidation hold is active. An Analyst may initiate the run; only the constrained backend routine may allocate a ledger posting or change workflow state. A Reviewer cannot override duplicate, reversal, currency, unexplained amount, timing or policy blockers with a reason.
- A successful business transition, case version, active allocation change, immutable submission/decision record, required audit event and idempotent result commit in one SQL transaction. A failed audit insertion rolls back the transition. A repeated identical request returns the saved result without a duplicate event. Realtime notifications and frontend playback are not evidence of a commit.
- Before granting a signed evidence link, verify current membership and object-to-workspace/case association. Only metadata IDs and hashes appear in audit rows; passwords, JWTs, API keys, signed links and binary contents do not.

## Contract examples to test downstream

1. Analyst A creates and submits a synthetic case. Reviewer B may return or approve a current eligible submission; A cannot approve after their role later changes to Reviewer.
2. Analyst A calls `approve` directly with a crafted JSON body. The backend returns 403, even if the UI button is hidden, and no decision/allocation/audit success is written.
3. An exact SGD 125 low-risk source/ledger pair within the inclusive window and without a conflicting allocation may auto-match. Reopening sets `needs_revalidation`; repeating the run cannot silently reclose it.
4. Workspace A user supplies a Workspace B case or evidence UUID. The read returns no row/404; a protected mutation returns 404 without identifying Workspace B.
5. Two reviewers race to approve the same case or allocate the same posting. One committed result wins; the other receives 409, with no partial state or duplicate audit outcome.

These are implementation acceptance cases for SCRUM-38–51. They are not claims that the present prototype enforces them.
